# koi 공용 AI 작업 지침

이 파일은 도구별 지침이 아니라 koi 저장소를 다루는 모든 코딩 에이전트의 로컬 정본이다.
코드 식별자와 공식 API 이름은 원문을 유지한다.

## 1. 작업 시작과 사실 확인

새 작업·새 세션에서는 루트 `AGENTS.md`와 이 파일을 순서대로 읽는다. 이후에는 작업과 직접
관련된 자료만 확인한다: `.ai/PLAN.md` → 대상 코드·테스트·설정·마이그레이션 → 관련
`.ai/spec/` → 필요할 때 최신 `.ai/records/`.

- `.ai/.backup-*`은 복구할 때만 읽고, 과거 `.claude/...`보다 같은 경로의 `.ai/...`를 우선한다.
- 실제 파일을 확인한 뒤 현재 사실을 말한다.
- 현재 구현은 코드·테스트·설정·마이그레이션, 다음 작업은 사용자 지시와 PLAN, 제품 의도는
  spec, 결정 맥락은 최신 record를 기준으로 삼는다.
- 문서와 코드가 충돌하고 결과·데이터·공개 동작이 달라지면 차이를 먼저 설명하고 판단을
  기다린다. 결과에 영향이 없는 오탈자는 합리적으로 처리하고 완료 보고에 적는다.

## 2. 수정 전 승인과 작업 단위

읽기·검색·로그 확인·브라우저 관찰·원인 분석은 바로 진행할 수 있다. 파일을 수정하기 전에는
`git status --short`를 확인하고 다음을 먼저 제시한 뒤 명시적인 승인을 기다린다.

- 결과와 성공 조건, 생성·수정·삭제할 파일
- 필요한 경우 서버·클라이언트·데이터 경계와 선택지의 대가
- 10~30줄 단위로 나눈 작업 순서와 실행할 테스트·빌드·린트·브라우저 확인

- 직접 작성·수정하는 코드는 테스트를 포함해 10~30줄을 기준으로 한다. 포맷 변경·자동 생성
  파일·lockfile은 예외다.
- 하나의 단위에는 하나의 목적과 독립적인 검증 방법을 둔다. 10줄 미만에서 자연스럽게
  끝나면 늘리지 않고, 30줄을 넘으면 나누거나 이유를 설명하고 다시 승인받는다.
- 승인한 범위 안에서만 진행하고, 범위가 커지면 파일·변경량·검증 방법을 다시 설명한다.
- 한 단위가 끝나면 결과와 남은 일을 설명하고 다음 단계로 자동 진행하지 않는다. 질문은
  한 번에 하나씩 한다.
- 설치·마이그레이션 실행·배포·커밋·push는 요청받은 경우에만 한다. 삭제나 되돌리기 어려운
  작업은 대상을 확인하고 별도로 알린다.

## 3. 구현 원칙

- 추측보다 로그·브라우저·실측을 우선한다. 버그는 재현 조건을 만들고 같은 조건으로 수정
  결과를 확인한다.
- 증상이 여러 개면 공통 원인을 먼저 찾고, 가능한 원인을 너무 빨리 하나로 좁히지 않는다.
- 가역적인 결정은 미루고 되돌리기 어려운 결정은 먼저 검증한다.
- 타입·DB 제약·테스트로 조용히 틀리는 상태를 막는다. 세 번째 반복 전에는 추상화하지 않는다.
- 대량 변환은 원본과 결과를 비교할 방법을 먼저 마련한다. 실제 증거가 없으면 완료라고
  말하지 않는다.

## 4. 프로젝트 기술·데이터 규칙

### Next.js·React

- 버전은 `package.json`에서 확인하고, 코드 작성 전 관련 `node_modules/next/dist/docs/`를 읽는다.
- 서버 컴포넌트를 기본으로 하며 상태·이벤트·브라우저 API가 필요한 가장 작은 경계에만
  `"use client"`를 둔다.
- `typedRoutes: true`를 지키고, `params`·`searchParams`는 Promise로, 라우트 props는 생성된
  `PageProps`·`LayoutProps`로 다룬다. 존재하지 않는 경로를 캐스트로 숨기지 않는다.
- 네비게이션 정본은 `libs/constants/routes.ts`의 `navItems`다. 초기 데이터 로딩에
  `useEffect` + `fetch`를 쓰지 않고 요청에 맞는 서버 경계를 고른다.
- 새 코드에 `pages/`, `getServerSideProps`, `next/head` 같은 이전 Router 관례를 들이지 않는다.

### 공용 코드

- Tailwind CSS v4 토큰은 `app/globals.css`의 `@theme`에 두고, 클래스 병합은 `cn()`, 내부
  경로는 `@/`를 사용한다.
- 새 상태 관리·데이터 페칭·테스트·E2E 도구는 기존 도구로 부족한 이유를 설명하고 승인받는다.

### Supabase·데이터 경계

- 서버에서는 `libs/db/server.ts`의 요청별 클라이언트를 쓰고, 브라우저 클라이언트는 OAuth처럼
  브라우저가 해야 하는 작업에만 쓴다. 인증 쿠키 갱신은 `proxy.ts`의 책임이며, 캐시·쿠키
  전달을 근거 없이 단순화하지 않는다.
- DB 변경은 새 마이그레이션으로 남기며 RLS·소유권·제약을 함께 검토한다. 폼 검증은 안내일
  뿐이므로 서버 입력은 신뢰 경계에서 다시 `safeParse`한다.
- snake_case 변환은 `libs/db/`에 두고, 스토리지 세부 사항은 전용 어댑터에 가둔다. DB에는
  스토리지 경로만 저장한다.

### 도메인 안전장치

- 집·카페 기록은 하나의 `brews` 모델에서 `type`으로 구분하고, 입력 흐름은 분리하며 검증된
  작은 primitive만 공유한다.
- 원두 이름은 식별자가 아니다. `bean_id` 연결과 `bean_name` 시점 스냅샷을 임의로 합치거나
  제거하지 않는다.
- D+n·잔량·단가 같은 파생값은 저장하지 않는다. 계산 불가는 `undefined`, 화면 표현은 화면에서
  정한다. `weight`는 선택값이고 `archived`는 사용자가 정한다.
- 명세와 스키마의 값 범위가 다르면 조용히 정규화하지 말고 관련 기록까지 확인한다.

## 5. 검증

먼저 변경과 가장 가까운 검증을 실행하고, 영향 범위에 따라 넓힌다.

- `pnpm test`: `libs/**/*.test.ts`의 순수 스키마·유틸 함수
- `pnpm build`: TypeScript, Next.js 빌드, typed route와 서버/클라이언트 경계
- `pnpm dev`와 `pnpm build`를 동시에 실행하지 않는다. 둘이 같은 `.next`를 쓰면 개발 서버와
  빌드 산출물이 서로 깨질 수 있다. Turbopack 빌드가 환경 제한으로 실패하면
  `pnpm exec next build --webpack`을 대체 경로로 실행하고 이유를 기록한다.
- `pnpm lint`: 정적 규칙과 코드 품질
- 브라우저 확인: UI 변경 경로와 viewport를 명시한다. 기본은 모바일·데스크톱이며
  반응형 경계를 건드렸다면 태블릿도 확인한다. 코드 변경 뒤에는 HMR 상태를 가정하지 말고
  대상 경로를 새로 고친 다음 DOM·스크린샷을 확인한다.
- DB·인증 변경: 로컬 명령만으로 증명되지 않는 Dashboard, 쿠키, RLS 확인 항목을 분리해 적는다.

문서만 바꿨다면 전체 앱 검증을 의식적으로 생략할 수 있다. 대신 경로, 링크, ignore 상태,
관리 블록 같은 정적 조건을 검사한다. 실행하지 못한 검증은 통과했다고 쓰지 말고 이유와
사용자가 확인할 방법을 남긴다.

## 6. 설명·완료 보고·문서

- 사용자의 현재 질문에 먼저 답하고, 현재 구현·이번 작업·이후 작업을 구분한다. 무관한
  미래 개념·용어·선택지를 미리 꺼내지 않는다.
- 새 개념·문법·타입·API는 필요해지는 순간에 하나씩 설명한다. 확정되지 않은 선택을
  필수 요구사항처럼 말하지 않는다. 이해하지 못했다는 피드백에는 새 용어 대신 쉬운 말과
  하나의 구체적인 흐름으로 다시 설명한다.
- 코드 설명은 변경 규모에 맞춰 목적, 입력→출력, 핵심 조건, 없을 때의 문제, 선택 이유와
  대안을 다룬다. 모든 줄이 아니라 판단에 영향을 주는 부분만 설명한다.
- 완료 보고에는 결과, 변경 파일별 역할, 실제 검증 결과, 남은 위험, 미완료 작업을 적는다.
- 복잡한 흐름은 ASCII로 설명하고, 이미지가 실질적으로 더 명확할 때만 제안 후 승인받는다.

### 프로젝트 문서

- `.ai/PLAN.md`에는 아직 끝나지 않은 작업과 미결정 사항만 둔다.
- 완료된 항목은 PLAN에서 제거하고 같은 날짜 record에 결과·근거·검증을 남긴다.
- PLAN의 판단 이유는 핵심 세 줄 이내로 유지하고 긴 탐구 과정은 record로 옮긴다.
- `.ai/records/YYYY-MM-DD.md`는 Asia/Seoul 날짜를 사용한다. 과거 판단을 조용히 다시 쓰지
  말고, 잘못을 발견하면 새 기록에 무엇이 왜 바뀌었는지 남긴다.
- `.ai/spec/`는 제품 동작이나 승인된 설계가 바뀔 때만 갱신한다.
- 코드로 강제할 수 있는 규칙은 타입·테스트·DB 제약·가까운 코드 주석으로도 옮긴다.
- 관련 문서 변경은 처음 승인 요청의 파일 목록에 포함한다.
- 루트 `AGENTS.md`에는 상세 규칙을 복제하지 않고 발견용 연결만 유지한다.

### 공개 추적 범위

이 프로젝트의 공개 전환 기준에 따라 검토된 Markdown 지침·계획·설계·작업 기록은 Git에
추적한다. 따라서 `.ai/AGENTS.md`, `.ai/CLAUDE.md`, `.ai/PLAN.md`, `.ai/spec/**/*.md`,
`.ai/records/**/*.md`가 공개 문서 범위다.

복구용 `.ai/.backup-*`과 `*.dc.html` 같은 export 산출물은 계속 ignore한다. 새 기록이나
명세에는 비밀값·개인 로컬 경로·불필요한 계정 정보를 넣지 않고, 공개해도 되는 프로젝트
판단과 검증 근거만 남긴다.
