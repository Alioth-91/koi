# koi 공용 AI 작업 지침

이 파일은 도구별 지침이 아니라 koi 저장소를 다루는 모든 코딩 에이전트의 로컬 정본이다.
코드 식별자와 공식 API 이름은 원문을 유지한다.

## 1. 새 작업을 시작할 때 읽는 범위

새 작업이나 새 세션마다 먼저 루트 `AGENTS.md`, 이어서 이 파일을 다시 읽는다. 같은 작업 안에서는
이미 읽은 지침을 반복하지 말고, 이후 문서는 작업과 관련된 범위만 다음 순서로 확인한다.

1. `.ai/PLAN.md`의 현재 할 일과 미결정 사항
2. 변경 대상 코드·테스트·설정·마이그레이션
3. 관련 기능의 `.ai/spec/` 문서
4. 결정 이유가 필요할 때 최신 관련 `.ai/records/YYYY-MM-DD.md`

- `.ai/.backup-*`은 복구 전용이다. 현재 판단의 근거로 읽거나 수정하지 않는다.
- 과거 문서의 `.claude/...`는 이전 폴더명이다. 같은 상대 경로의 `.ai/...`를 먼저 찾는다.
- 문서 전체를 읽었다고 가정하지 말고, 실제로 확인한 파일을 근거로 말한다.

## 2. 현재 사실과 앞으로의 의도를 구분한다

- **현재 구현:** 코드, 테스트, 설정, 마이그레이션이 말한다.
- **다음 작업:** 현재 사용자 지시와 `.ai/PLAN.md`가 말한다.
- **제품 의도:** 관련 `.ai/spec/`가 말한다.
- **결정 맥락:** 최신 관련 record가 말한다.

문서와 코드가 다르면 무조건 한쪽을 믿지 않는다. 작성 날짜와 실제 구현을 대조한다.
충돌이 결과·데이터·공개 동작을 바꿀 수 있으면 수정 전에 차이를 설명하고 사용자의 판단을
기다린다. 오탈자처럼 결과를 바꾸지 않는 차이는 합리적으로 처리하고 완료 보고에 밝힌다.

## 3. 파일 수정 전 승인 — 하드 게이트

읽기, 검색, 로그 확인, 브라우저 관찰, 원인 분석 같은 읽기 전용 조사는 바로 진행한다.
읽기·검토·보고 요청은 그 자체로 파일 수정 승인을 뜻하지 않는다. 코드·테스트·설정·문서를
수정하기 전에는 `git status --short`로 기존 변경을 확인하고, 다음 내용을 먼저 제시한다.

- 만들 결과와 확인 가능한 성공 조건
- 생성·수정·삭제할 파일
- 코드 변경과 직접 관련될 때만 서버/클라이언트·데이터 경계
- 결과를 바꿀 수 있는 선택지와 대가
- 주요 코드가 30줄을 넘지 않도록 나눈 작업 단위
- 실행할 테스트·빌드·린트·브라우저 확인

그 뒤 **명시적인 승인**을 기다린다. 승인 후에도 새 파일, 패키지, 데이터베이스 변경,
외부 서비스 조작처럼 범위가 실질적으로 늘어나면 멈추고 다시 승인받는다.

- 모호함이 결과를 크게 바꾸고 저장소에서 답을 찾을 수 없을 때만 질문한다.
- 질문은 한 번에 하나씩 한다.
- 설치, 마이그레이션 실행, 배포, 커밋, push는 사용자가 범위에 넣지 않았다면 하지 않는다.
- 삭제나 되돌리기 어려운 작업은 정확한 대상을 확인하고 별도로 알린다.

## 4. 10~30줄 작업 단위

- 승인 한 번당 직접 작성·수정하는 코드는 10~30줄을 기준으로 한다. 테스트 코드도 같은 단위로
  나누며, 포맷 변경·자동 생성 파일·lockfile은 예외로 둔다.
- 하나의 개념이 10줄 미만에서 자연스럽게 끝나면 억지로 늘리지 않는다.
- 30줄을 넘을 것 같으면 독립적으로 검증 가능한 단위로 나누고, 나누기 어려운 이유가 있으면
  변경 전에 설명한 뒤 재승인받는다.
- 줄 수를 맞추려고 하나의 책임을 부자연스럽게 쪼개거나 서로 다른 개념을 묶지 않는다.
- 각 단위는 성공 조건 하나와 그에 맞는 확인 수단을 가진다.

## 5. 판단과 진단 원칙

- 추측하기 전에 로그·브라우저·실측으로 확인한다.
- 버그는 재현 조건을 한 문장으로 만들고, 수정 뒤 같은 조건에서 사라졌는지 확인한다.
- 증상이 여러 개면 공통 원인을 먼저 찾는다.
- 가능한 원인을 너무 일찍 하나로 좁히지 않는다.
- 가역적인 결정은 필요할 때까지 미루고, 되돌리기 어려운 결정은 먼저 검증한다.
- 타입·DB 제약·테스트로 “빌드는 초록인데 결과는 조용히 틀린 상태”를 차단한다.
- 계산할 수 있는 값은 저장하지 않고 정본을 하나만 유지한다.
- 세 번째 반복 전에는 성급하게 훅·헬퍼·컴포넌트로 추상화하지 않는다.
- 선택한 방법뿐 아니라 검토하고 버린 방법과 그 대가도 설명한다.
- 대량 치환이나 변환 스크립트는 원본·백업과 결과를 비교할 방법부터 만든다.
- 작업 전에 성공 조건을 정하고, 실제 증거가 확인될 때만 완료라고 말한다.

## 6. 프로젝트의 안정적인 기술 규칙

### Next.js와 React

- 현재 Next.js·React 버전은 `package.json`에서 확인한다. 기억에 의존하지 말고
  코드를 쓰기 전에 관련 `node_modules/next/dist/docs/` 문서를 읽는다.
- 서버 컴포넌트를 기본으로 한다. 상태, 이벤트, 브라우저 API가 필요한 가장 작은 경계에만
  `"use client"`를 둔다. 경계를 새로 만들거나 옮기면 이유를 한 줄로 설명한다.
- `typedRoutes: true`다. 존재하지 않는 경로를 `as Route` 캐스트로 숨기지 않는다.
- `params`와 `searchParams`는 Promise로 다루고 필요할 때 `await`한다.
- 라우트 props는 생성된 `PageProps<'/...'>`, `LayoutProps<'/...'>`를 우선한다.
- 네비게이션 항목의 정본은 `libs/constants/routes.ts`의 `navItems`다.
- 초기 데이터 로딩에 `useEffect` + `fetch`를 쓰지 않는다. 서버 컴포넌트, 서버 액션,
  라우트 핸들러 중 요청의 성격에 맞는 경계를 고른다.
- `pages/`, `getServerSideProps`, `next/head` 같은 이전 Router 관례를 새로 들이지 않는다.

### 스타일과 공용 코드

- Tailwind CSS v4다. 토큰은 `app/globals.css`의 `@theme`에서 관리하며
  `tailwind.config.js`가 있다고 가정하지 않는다.
- 조건부 클래스 병합은 `libs/utils.ts`의 `cn()`을 사용한다.
- 내부 경로 별칭은 `@/`다.
- 상태 관리, 데이터 페칭, 컴포넌트 테스트, E2E 도구를 새로 도입하려면 먼저 필요성과
  기존 도구로 해결할 수 없는 이유를 제시하고 승인받는다.

### Supabase와 데이터 경계

- 서버 컴포넌트·서버 액션·라우트 핸들러에서는 `libs/db/server.ts`의 요청별 클라이언트를 쓴다.
- 브라우저 클라이언트는 OAuth 이동처럼 브라우저가 실제로 해야 하는 작업에만 쓴다.
- 인증 쿠키 갱신은 `proxy.ts`의 책임이다. 캐시 방지 헤더와 request/response 쿠키 전달을
  근거 없이 단순화하지 않는다.
- DB 구조 변경은 새 마이그레이션으로 남기고 RLS, 소유권 조건, 제약을 함께 검토한다.
- 폼 검증은 사용자 안내이고 서버 검증은 신뢰 경계다. 서버 입력은 다시 `safeParse`한다.
- DB의 snake_case와 도메인 타입 변환은 `libs/db/` 어댑터 경계에 모은다.
- 저장소 조작이 생기면 Supabase 세부 사항을 전용 어댑터에 가두고 DB에는 경로만 저장한다.

### 도메인 안전장치

- 집 기록과 카페 기록은 DB의 단일 `brews` 모델에서 `type`으로 구분한다. 입력 UI는 서로
  다른 흐름을 유지하고, 검증된 작은 primitive만 공유한다.
- 원두의 이름은 식별자가 아니다. DB의 `bean_id` 연결과 `bean_name` 시점 스냅샷은 서로
  다른 책임이므로 하나를 임의로 제거하지 않는다.
- D+n, 잔량, 단가 같은 파생값은 저장하지 않는다. 계산 불가 상태는 계산 계층에서
  `undefined`로 두고 `"-"` 같은 표현은 화면에서 정한다.
- 원두의 `weight`는 선택값이고 `archived`는 사용자가 정한다. 잔량만으로 자동 보관하지 않는다.
- 명세의 값 범위와 현재 스키마가 다르면 조용히 정규화하지 말고 관련 기록까지 확인한다.

## 7. 검증 기준

먼저 변경과 가장 가까운 검증을 실행하고, 영향 범위에 따라 넓힌다.

- `pnpm test`: `libs/**/*.test.ts`의 순수 스키마·유틸 함수
- `pnpm build`: TypeScript, Next.js 빌드, typed route와 서버/클라이언트 경계
- `pnpm dev`와 `pnpm build`를 동시에 실행하지 않는다. 둘이 같은 `.next`를 쓰면 개발 서버와
  빌드 산출물이 서로 깨질 수 있다. Turbopack 빌드가 환경 제한으로 실패하면
  `pnpm exec next build --webpack`을 대체 경로로 실행하고 이유를 기록한다.
- `pnpm lint`: 정적 규칙과 코드 품질
- 브라우저 확인: UI 변경 경로와 viewport를 명시한다. 기본은 모바일·데스크톱이며
  반응형 경계를 건드렸다면 태블릿도 확인한다. 코드 변경 뒤에는 HMR 상태를 가정하지 말고
  대상 경로를 새로 고친 다음 DOM·스크린샷을 확인한다.
- DB·인증 변경: 로컬 명령만으로 증명되지 않는 Dashboard, 쿠키, RLS 확인 항목을 분리해 적는다.

문서만 바꿨다면 전체 앱 검증을 의식적으로 생략할 수 있다. 대신 경로, 링크, ignore 상태,
관리 블록 같은 정적 조건을 검사한다. 실행하지 못한 검증은 통과했다고 쓰지 말고 이유와
사용자가 확인할 방법을 남긴다.

## 8. 설명과 완료 보고

- 코드보다 판단을 먼저 보여준다.
- 처음 등장하는 문법·타입·API는 이름, 하는 일, 필요한 이유를 설명한다.
- 코드와 로직을 설명할 때는 목적, 해결하는 문제, 사용하지 않을 때의 사이드 이펙트,
  검토한 대안과 선택 이유, 입력부터 출력까지의 흐름을 함께 말한다.
- 핵심 코드의 각 줄이나 조건은 왜 필요한지와 삭제했을 때의 영향을 설명한다.
- 작업 완료 보고에는 결과, 변경 파일과 파일별 역할, 실제 검증 결과, 남은 위험,
  아직 하지 않은 작업을 포함한다.
- 복잡한 코드 흐름은 채팅 안의 ASCII 상자와 화살표로 설명한다. 단순한 변경은 prose로 충분하다.
- 구조가 복잡해 실제 이미지가 훨씬 명확할 때만 이미지 형식을 먼저 제안하고 승인받는다.

예시:

```text
[사용자 입력]
      |
      v
[Server Action] --검증 실패--> [폼 오류]
      |
      v
[Supabase Auth]
      |
      v
[쿠키 갱신] --> [보호된 화면]
```

## 9. PLAN·records·spec 관리

- `.ai/PLAN.md`에는 아직 끝나지 않은 작업과 미결정 사항만 둔다.
- 완료된 항목은 PLAN에서 제거하고 같은 날짜 record에 결과·근거·검증을 남긴다.
- PLAN의 판단 이유는 핵심 세 줄 이내로 유지하고 긴 탐구 과정은 record로 옮긴다.
- `.ai/records/YYYY-MM-DD.md`는 Asia/Seoul 날짜를 사용한다. 과거 판단을 조용히 다시 쓰지
  말고, 잘못을 발견하면 새 기록에 무엇이 왜 바뀌었는지 남긴다.
- `.ai/spec/`는 제품 동작이나 승인된 설계가 바뀔 때만 갱신한다.
- 코드로 강제할 수 있는 규칙은 타입·테스트·DB 제약·가까운 코드 주석으로도 옮긴다.
- 관련 문서 변경은 처음 승인 요청의 파일 목록에 포함한다.
- 루트 `AGENTS.md`에는 상세 규칙을 복제하지 않고 발견용 연결만 유지한다.

## 10. 공개 저장소에서 `.ai/`의 추적 범위

이 프로젝트의 공개 전환 기준에 따라 검토된 Markdown 지침·계획·설계·작업 기록은 Git에
추적한다. 따라서 `.ai/AGENTS.md`, `.ai/CLAUDE.md`, `.ai/PLAN.md`, `.ai/spec/**/*.md`,
`.ai/records/**/*.md`가 공개 문서 범위다.

복구용 `.ai/.backup-*`과 `*.dc.html` 같은 export 산출물은 계속 ignore한다. 새 기록이나
명세에는 비밀값·개인 로컬 경로·불필요한 계정 정보를 넣지 않고, 공개해도 되는 프로젝트
판단과 검증 근거만 남긴다.
